# Branch protection: main, dev, master and future branches

Branch protection is configured **per repository** in a personal account. Reusable workflows do not activate it. No Organization is necessary, but each repository requires an authorized admin action.

### Generate a reviewable ruleset

Run locally (the script has no network/write operations):

```bash
python scripts/render_ruleset.py --branch main \
  --checks 'Audit · Lint · Type-check · Unit · Dual build' \
           'Playwright · Desktop & mobile · Accessibility' \
           'Secret scan' 'Supabase migrations · RLS contract' 'Vercel' \
  --strict --output ./main-ruleset.json

python scripts/render_ruleset.py --branch dev \
  --checks 'verify' 'Vercel – example-web' 'Vercel – example-api' \
  --output ./dev-ruleset.json

python scripts/render_ruleset.py --branch master --checks 'build' \
  --output ./master-ruleset.json
```

**The names above are examples:** verify the exact names from a recent successful commit before importing; never blindly require a check that never runs. Each repository may have a different set of required checks and different applicable environments. If only `verify` is protected and `verify` already verifies both Vercel deployments, that is acceptable — avoid accidentally circular or duplicate check dependencies.

1. Open `https://github.com/Nisan-Sinai/REPOSITORY/settings/rules`.
2. Choose **New ruleset → Import a ruleset** (or equivalent GitHub settings UI).
3. Upload the generated JSON and verify scope/required checks, then **Create** after explicit approval.
4. Check the actual branch `protected` status and test one harmless PR. For ruleset JSON import quirks, correct the JSON before proceeding. Some plans/roles may not allow every rule type.

Rules generated by the helper require PRs, resolved discussions, linear history, prohibit deletion/force push, and can require the exact CI/Vercel checks. Approval count defaults to zero so solo-maintainer and carefully guarded Dependabot merges continue to work; add 1 reviewer only after there is an eligible *different* reviewer. `--strict` requires PRs to be up-to-date — it may temporarily block Dependabot PRs that need rebasing.

### Never weaken protection for automation

- Existing jobs must stay required until verified replacements are ready.
- Do not use admin bypass to merge red CI.
- Do not automatically apply one universal checklist to unrelated tech stacks.
- Reusable workflow names/jobs may produce different check names in callers; inspect the first successful run before changing rulesets.
- GitHub Actions `GITHUB_TOKEN` does **not** have repo-admin permission to modify branch protection.
- The existing `nisan-sinai-technologies` protections **were prepared in PR #56 but require separate activation**; a JSON file alone doesn't protect its `main` branch.

## Optional admin CLI (opt-in, never runs in GitHub Actions)

A separate CLI can **create** one reviewed ruleset on one personal repository, and will not update/delete existing rules. Its default is an offline dry-run:

```bash
python scripts/admin_ruleset.py --repo Nisan-Sinai/EXAMPLE --file ./main-ruleset.json
```

Only after an administrator authorizes it and securely supplies a short-lived, narrowly-scoped `GITHUB_ADMIN_TOKEN` (fine-grained repository Administration write permission), run:

```bash
python scripts/admin_ruleset.py --repo Nisan-Sinai/EXAMPLE --file ./main-ruleset.json \
  --apply --confirm Nisan-Sinai/EXAMPLE
```

Never run it from an untrusted pull request, never store the token in the public hub, and never interpret this tool as applying policies to every repository automatically. Review one repository at a time; use the GitHub UI if preferred.
